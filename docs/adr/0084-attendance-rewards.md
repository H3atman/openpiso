# ADR-0084: Attendance Rewards — Account-bound daily time

- Status: Proposed (S1–S6 implementation; canonical automated assertions passed; S7 manual/release merge-gate evidence pending)
- Date: 2026-09-24
- Deciders: shop owner (product)
- Relates to: [ADR-0001](0001-time-ownership.md), [ADR-0003](0003-points-economy.md), [ADR-0014](0014-reporting-model.md), [ADR-0015](0015-audit-log.md), [ADR-0052](0052-coin-promo.md), [ADR-0053](0053-shop-hours.md), [ADR-0054](0054-backup-and-restore.md), [ADR-0058](0058-audit-derived-web-admin-notifications.md), [ADR-0069](0069-rejection-credit.md), [ADR-0085](0085-migration-version-guard.md)

## Context

Customers need a daily reason to return without changing paid time, Points, Coin Promo, or Guest Claim. Attendance is an Account-only, separately accounted time liability. The Admin's SQLite database and host clock, not a Client, decide qualification, dates, claims, and expiry. S1–S6 implementation is recorded here; canonical automated scenario assertions pass. S7 remains open pending installed-release acceptance and rollback rehearsal.

## Decision

### Earning and eligibility

Attendance Reward ships disabled with a 1,000-cent daily threshold, 3,600-second Check-In award and one following calendar-month claim window. Accepted Account Coin Events qualify at server commit; Account-targeted Rejection Credits qualify using original rejection instant, frozen Account attribution and effective configuration, only if Attendance was enabled and Shop Open then. Guest coins, Claims, Vouchers, adjustments, redemptions, and wheel prizes do not qualify. Checked integer cents accumulate per Account/Admin-local date across PCs and sessions, never across midnight. Each admitted Contribution records the settings version selected by its transaction; the first admitted Contribution freezes that date's threshold and reward. A rebuild uses that stored version rather than inferring configuration from `source_at`, which may predate admission after a host-clock regression. One immutable Check-In per Account/date is awarded at threshold. Further value cannot award twice.

A completed date is eligible only when Account existence, enabled Attendance and effective Shop Open overlap at least once. Disabled Shop Hours means Shop Open; overnight periods and Shop Overrides count. Freeze completed eligibility as normalized, sorted, disjoint half-open UTC intervals (merge touching intervals), with one restart-observed UTC offset per date; interval boundaries carry no separate offsets. A late Credit can turn a missed eligible date into an earned date without rewriting its eligibility.

### Settings and calendar authority

Every real settings edit appends a complete immutable version at server commit; identical input is a no-op before stale-version comparison, changed stale input conflicts with HTTP 409 `{ "error": "attendance_settings_stale", "current_version": int }`. On a structured stale conflict, the Owner UI loads current settings and reports the failed save without replaying the stale draft; the owner reviews/re-enters any desired changes before committing again. Threshold cents and reward seconds are positive checked integers; owner-entered reward minutes convert to seconds; claim window is 1–120 months. Every Contribution stores the configuration version selected at admission. The first Contribution fixes its Account/date award snapshot, and projection rebuilds read the first admitted Contribution's recorded version rather than re-resolving its possibly regressed `source_at`. An Earning Month exists only after its first Check-In and freezes the claim-window version effective at its local month start; if that instant predates every version during initial rollout, it uses the earliest immutable version. Its claim starts at the following local month's midnight, stores inclusive local start/end dates, and has an exclusive UTC deadline; later edits cannot change those bounds. Configuration and Shop Hours/Override evidence are append-only.

The clock singleton persists a UTC floor and monotonic open local Attendance date. Authority uses max(host UTC, floor), converted in the current host timezone; a completed date never reopens and crossed deadlines never revive. Backward clock/timezone regression assigns new Contributions to the last open date until catch-up without withholding coin credit. Before a read exposes newly expired state, or a mutation that can advance expiry, advance the floor under `BEGIN IMMEDIATE`. The unchanged one-second timer path reads the singleton and returns without a write transaction; source mutations persist the floor in their own transaction, and a date rollover finalizes under `BEGIN IMMEDIATE`. Forward jumps finalize skipped completed dates from immutable evidence; runtime discontinuity is diagnostic, with a standing Web Admin advisory while regression persists, not a Client or audit event. Frozen dates and deadlines are never recalculated.

### Claim, expiry, and reporting

Attendance Time belongs to the Account, does not drain or transfer, and only enters Remaining Time through an authenticated, atomic full claim of one Earning Month's currently outstanding seconds. No partial or zero claim. A globally unique request UUID retried for the same Account/month returns its original result without double credit; reuse elsewhere conflicts. Authenticated domain denials are audited with typed reasons and no deltas; inactive or deleted Accounts fail unaudited. A late Check-In can permit a supplemental claim before deadline. Disabling earning does not disable claims; an already authenticated Account can claim while Shop Closed, including from a zero-time Lock. Refresh the Active Session binding after commit; SQLite remains authoritative if refresh fails. Expiry is derived from the exclusive deadline, not a scheduler or mutable status. Deletion allocates only outstanding seconds per month as forfeiture in its transaction; `account_deleted` carries the aggregate negative Attendance delta, expiry wins before deletion, no separate forfeiture event is added, historical identity survives, and re-import starts a new identity.

The append-only canonical Audit Log gains a nullable `attendance_seconds_delta`, separate from `seconds_delta`. Successful Check-Ins add Attendance Time, successful Claims subtract it and add Remaining Time, and deletion subtracts outstanding Attendance Time; authenticated claim denials have typed reasons and no deltas. Expiry has no event. Attendance events are Silent; Check-In/Claim classify Time and settings edits Admin. Successful event/detail links are one-to-one. Earned = claimed + outstanding + expired + forfeited; claimable is a subset of outstanding. Earned flow follows original local earning date, claimed flow claim instant, expired flow deadline and forfeited flow deletion instant. Claims alone enter Free Time Dispensed; Cash Revenue and Points are unchanged. Liability belongs to Account, never PC or pesos.

At threshold spend, the informational Attendance Effective Bonus % is `floor(reward_seconds * 10_000 / floor(threshold_cents * rate_seconds / rate_amount_cents))`. Zero base seconds displays `∞` and unsafe; finite results are not judged against `unsafe_bonus_bps`, cannot block save, and do not enter the account worst case. Attendance is a daily step reward, not a per-peso rate.

The S4 typed repository report reads Attendance facts in one SQLite `BEGIN IMMEDIATE` transaction and calls the shared finalizer before deriving deadline-based expiry. Its `as_of` is the returned durable floor, so expired state cannot revive after a clock regression. A report may advance the clock floor and finalize crossed calendar dates, but writes no Audit Log rows. It captures one `as_of`, `admin_local_date`, and `admin_local_month`. Day/week/month flows honor the selected Admin-local date range; Earning Month and Account pages paginate independently (default 50, maximum 200), while current Account liability is range-independent. The report includes a clock-regression advisory and effective-bonus economics using the latest Attendance settings version and active Shop Rate.

### API and Client surface

S6 exposes `GET /api/attendance`, `GET /api/attendance/months/{earning_month}`, and `POST /api/attendance/claims` on `:3210`, guarded by AccountSession; the bearer token identifies the Account, and a claim selects only an Earning Month and request UUID while the server derives value, dates, and deadlines. OwnerSession guards `GET`/`PUT /web-admin/attendance/settings`, `POST /web-admin/attendance/settings/preview`, and `POST /web-admin/reports/attendance` on `:8080`. Stale settings return `attendance_settings_stale` with the current version; authenticated claim denials return typed `attendance_claim_denied` reasons. Client payload and error details are in [the API reference](../api.md#daily-reward); owner settings and report contracts are documented in the same reference.

The additive Heartbeat `attendance_supported` flag gates the Client's Daily Reward strip/calendar and claim surface, including on the zero-time Lock. A new Client defaults to unsupported until a flag arrives and preserves cached support when an older Admin omits it; old Clients ignore the additive field. The Client renders server state and has no Attendance authority.

### Durability and rollout

All read-then-write operations reserve the SQLite writer before capturing their instant. Source, progress, Check-In, Earning Month and audit commit together; settings/Shop Hours/Override evidence and audit commit together; Claim and balance/audit/detail commit together; deletion and forfeiture/audit commit together. Claim and deletion advance the durable clock floor in the same transaction and derive expiry from max(host UTC, saved floor). Immutable Contributions rebuild only capped daily progress, using the stored configuration version on the first admitted Contribution for each Account/date. S1 establishes settings v1, Shop Hours/Override evidence, clock/calendar/intervals and Backup Set mapping; S2 earning, S3 claim/forfeiture, S4 reporting, S5 owner controls, S6 Client surface, S7 documentation/verification close-out. No owner enable path ships before earning, claim, forfeiture, reporting and advisory. Disabled coin paths must remain unchanged and produce no Attendance writes.

S2 uses one transaction-level finalizer; the pool-level finalizer wraps it. Startup calls it before checking the daily-progress projection, the one-second timer reads the clock singleton and skips the write transaction when the local date is unchanged, and coin/Rejection Credit transactions call it only when Attendance is enabled. Production call sites use the shared `attendance::host_offset()` helper; tests supply an explicit `FixedOffset`. Accepted Account coins qualify when their local earning date has any effective Shop Open overlap, not only when the commit instant is open. The Rejection Credit hook checks Attendance enabled before reading the original rejection timestamp, then qualifies Shop Open and the historical configuration at that instant.

Migration seeds disabled v1 and current Shop Hours/still-active Override at one UTC instant; no historical source backfill. Backup Sets: Configuration holds settings and eligibility evidence; Accounts holds progress and Earning Months; Ledger holds Contributions, Check-Ins, Claims and forfeitures; Runtime State holds clock singleton. Full Restore replaces rather than merges; old full Backups migrate to empty disabled Attendance, partial exports cannot restore. Strict migration-history guard runs before seed/backup/migration. Pending migrations require a mandatory all-Set Pre-Migration Backup plus byte-exact companion. After migration or staged Restore, verify references, reconciliation, intervals/deadlines and Backup completeness; failed verification refuses startup, not automatic rollback. Startup rebuilds mismatched progress from immutable facts under `BEGIN IMMEDIATE`, but never synthesizes other damaged facts. Older Admin needs its matching Pre-Migration Backup rather than direct downgrade. Heartbeat `attendance_supported` is optional: a new Client defaults to unsupported until the first flag arrives, then preserves its cached value when older Admin responses omit the field; old Clients ignore the additive field, and new Clients hide Attendance on old Admin without declaring it offline.

## Consequences

Attendance adds a separate Account liability and historical evidence without changing paid-time authority. A forward clock jump may irreversibly expire claims; a backward jump conservatively holds the last open date. Full recovery from corrupt immutable facts requires a known-good full Backup. Canonical automated scenario assertions pass; this ADR remains Proposed pending manual/release acceptance, including upgrade from the latest released database, installed Client/Web Admin visual acceptance, and rollback rehearsal.
